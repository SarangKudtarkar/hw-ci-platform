Software teams ship with CI/CD. Chip teams can too. Follow a commit through lint, synthesis and simulation, see every build recorded and traceable, watch runtimes drift, and see how an AI assistant can read a failed build and explain it.

01Pipeline overview

Each commit runs through three quality stages. A failure stops the pipeline. Every build is stored, then shown on a dashboard. Click a block to learn what it does.

hw-ci-platform/
├─ flow/      lint.py · synth.py · simulate.py · pipeline.py
├─ db/       schema.sql · database.py · build.db
├─ analysis/  analytics.py
├─ dashboard/ app.py (Streamlit)
├─ app/       analyze entry point (AI failure analysis)
├─ tests/     pytest suite
├─ evals/     evaluation runs
├─ agent/ · tools/  (not described in the README)
└─ Jenkinsfile · pyproject.toml

02Run a build

Choose which stage should fail, then run. Watch the quality gate stop the pipeline and see the record that would be saved.

// build record appears here
Press Run. The flow runs Lint, then Synthesis, then Simulation, each only if the previous stage passed.

Stage runtimes and messages are samples. The record shows what the README says is stored per build: branch, commit SHA, overall status, total runtime and per-stage status and runtime.

Validation model (illustrative)


class FailureAnalysis(BaseModel):
    build_id: int
    failed_stage: Literal["lint", "synth", "sim"]
    root_cause: str
    suggested_fix: str
    confidence: float = Field(ge=0, le=1)

    
Tool names, log text and the schema are illustrative. The key ideas are real: the model can only read data through narrow read-only tools, and its answer must pass schema validation before anyone sees it.
